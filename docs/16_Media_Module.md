# 16 — Media Module

## Status

Architecture approved in principle. Detailed screen, API, database, storage, and processing specifications remain required before implementation.

## Purpose

The Media module is the central asset library for a PanoFolio Workspace.

Workspace Users upload assets once, manage them centrally, and attach them to Portfolio content or Experiences. Media must not be stored only as an invisible child of one Experience.

## Product goals

The Media module should:

- Provide one trusted location for Workspace assets
- Support large panorama upload from desktop browsers
- Prevent unnecessary duplicate uploads
- Allow an asset to be selected and reused where permitted
- Show where an asset is currently used
- Protect private and draft assets
- Support reliable processing, validation, and publishing
- Remain extensible for future immersive formats

## Ownership model

```text
Account
└── Workspace
    └── Media Assets
```

Each Media Asset belongs to exactly one Workspace in Version 1.

A Media Asset may be referenced by:

- Portfolio content
- Branding configuration
- One or more Experiences
- One or more Experience scenes
- Future approved content types

Ownership does not transfer when an asset is attached to an Experience.

## Approved Media types

The architecture supports these top-level types:

- Panorama
- Image
- Video
- Document

Version 1 implementation support for each type must be confirmed in the Development Roadmap. Architecture support does not automatically mean every type is implemented in the first release.

### Panorama

Examples:

- Equirectangular 360-degree image
- Scene source image
- Panorama preview image generated by processing

### Image

Examples:

- Portfolio cover
- Experience thumbnail
- Logo
- Profile image
- Gallery image
- Social sharing image

### Video

Examples:

- Portfolio introduction
- Experience media
- Future immersive video

Video upload, transcoding, streaming, and storage costs require a separate implementation decision.

### Document

Examples:

- Floor plan
- Brochure
- Information sheet
- PDF attachment

Public document delivery must be explicitly configured; uploaded documents are not public by default.

## Core workflow

The approved content workflow is:

```text
Upload Media
↓
Validate File
↓
Store Original
↓
Process Derivatives and Metadata
↓
Asset Becomes Available
↓
Create or Edit Experience
↓
Attach Existing Media
↓
Configure Scene, Order, and Interactions
↓
Publish
```

An Experience editor may provide an upload shortcut, but files uploaded there must still enter the central Workspace Media library.

## Asset states

Every Media Asset requires an explicit lifecycle state.

Recommended state model:

```text
Uploading
↓
Processing
↓
Ready | Failed
↓
Archived | Deleted
```

Additional publishing visibility is separate from processing state.

### Uploading

The original file is being transferred. The interface must show progress and allow supported cancellation or retry behavior.

### Processing

The upload completed and the system is validating metadata or generating required derivatives.

### Ready

The asset passed validation and can be selected for supported uses.

### Failed

Upload or processing failed. The interface must show a useful reason and a retry or replacement path where possible.

### Archived

The asset is retained but hidden from normal selection flows. Archiving must not silently break existing published references.

### Deleted

Deletion follows the approved usage and retention rules. It must not be treated as immediate permanent removal when recovery or asynchronous storage cleanup is required.

## Visibility model

A Media Asset is private to its Workspace by default.

Possible visibility outcomes include:

- Private Workspace asset
- Referenced by draft content
- Referenced by published content
- Public derivative available through a published Portfolio or Experience

Publishing an Experience does not automatically expose every original asset file. Public delivery should use approved derivatives or protected delivery paths.

## Reuse rules

The same Media Asset may be attached to multiple supported content records within the same Workspace.

Reuse must:

- Reference the existing asset record
- Avoid creating another original upload
- Preserve independent placement and presentation settings
- Maintain a usage index
- Prevent one content editor from unintentionally changing the underlying original for every usage

Presentation data such as crop, focal point, caption, scene order, hotspot placement, or display role belongs to the attachment or content relationship when it can differ by usage.

## Replacement rules

Replacing an original asset is a high-impact action because the asset may be used in multiple places.

Version 1 should distinguish between:

- Editing asset metadata
- Replacing an attachment in one Experience
- Replacing the underlying original asset everywhere

Global original replacement must not occur accidentally. It requires explicit confirmation and a usage-impact summary.

## Deletion rules

Before deletion, the system must determine whether the asset is in use.

### Unused asset

The user may delete it according to retention policy.

### Used by draft content

The interface must identify affected drafts and require confirmation or removal of references.

### Used by published content

The system must block destructive deletion by default and provide a safe resolution workflow.

A published Experience must never become silently broken because an asset was removed from the Media library.

## Usage tracking

The Media Asset Details screen must be able to show where an asset is used.

Usage records should identify:

- Portfolio or Experience
- Scene or content location
- Draft or published state
- Usage role, such as cover, thumbnail, panorama scene, logo, or document

Usage tracking must be derived from authoritative relationships, not only a manually maintained counter.

## Upload requirements

### Desktop-first

Media upload is designed primarily for desktop browsers.

The upload experience should support, subject to detailed design:

- File picker
- Drag and drop
- Multiple file selection
- Per-file progress
- Overall progress
- Validation before or during transfer
- Retry for failed files
- Duplicate warning
- Safe navigation warning during active uploads

### File validation

Validation must cover the requirements approved for each Media type, including:

- Allowed MIME type
- File extension consistency
- Maximum size
- Image dimensions
- Panorama aspect or projection requirements
- Corrupt or unreadable files
- Security scanning where required

Client-side checks improve feedback but do not replace server-side validation.

## Duplicate handling

The system should detect likely duplicate originals using a reliable server-side identifier such as a content checksum.

When a duplicate is detected within the same Workspace, the interface should offer an approved action such as:

- Use existing asset
- Upload as a separate asset when genuinely required
- Cancel upload

Filename alone is not sufficient duplicate detection.

## Panorama processing

Panorama assets may require:

- Projection validation
- Width and height extraction
- Aspect-ratio validation
- Preview generation
- Thumbnail generation
- Viewer-optimized derivatives or tiles
- Metadata extraction
- Processing status and error reporting

The original must be preserved according to storage policy. Public viewing should not require downloading an unnecessarily large original when optimized delivery is available.

## Image processing

Image assets may require:

- Dimension extraction
- Orientation normalization
- Thumbnail generation
- Responsive derivatives
- Metadata removal according to privacy policy
- Format optimization

The detailed derivative matrix belongs in the Media Processing specification.

## Metadata

A Media Asset should support core system metadata:

- Asset ID
- Workspace ID
- Media type
- Original filename
- Display title
- Description
- Alt text where applicable
- MIME type
- File size
- Width and height where applicable
- Duration where applicable
- Checksum
- Processing state
- Visibility state
- Storage reference
- Created by
- Created at
- Updated at

Type-specific metadata must be documented separately.

## Accessibility metadata

Images and relevant visual assets should support alt text.

Decorative usage may intentionally use empty alternative text at the attachment level. Therefore, default asset alt text and per-usage accessibility text may need to be distinct.

Videos require future decisions for captions, transcripts, and audio description.

## Media Library information architecture

The Workspace Media area contains:

- All Media
- Panoramas
- Images
- Videos
- Documents
- Upload action

The primary screen specifications are:

- `WSP-011 — Media Library`
- `WSP-012 — Media Upload`
- `WSP-013 — Media Asset Details`

## Media Library capabilities

The Media Library should eventually support:

- Grid and list presentation
- Search
- Type filtering
- Processing-state filtering
- Usage filtering
- Sort by upload date, filename, title, size, or usage where approved
- Multi-select
- Bulk archive or deletion for eligible assets
- Asset preview
- Asset details
- Select mode when opened from another editor

The exact Version 1 subset must be approved in the screen specification.

## Selection mode

When the Media Library is opened from Portfolio or Experience editing, it may operate in selection mode.

Selection mode must:

- Preserve the calling context
- Filter to compatible Media types
- Clearly state the required asset role
- Allow selection of existing compatible assets
- Allow upload without leaving the workflow
- Return the selected asset safely
- Avoid exposing destructive library actions unless intentionally included

## Permissions

A Workspace User may access only Media Assets owned by that Workspace.

Authorization must be enforced for:

- Listing
- Reading metadata
- Viewing private previews
- Uploading
- Editing metadata
- Attaching and detaching
- Archiving
- Deleting
- Accessing originals and derivatives

Possession of a guessed storage URL must not bypass authorization for private Media.

## Administrator access

Administrator Media access must be tied to approved support, moderation, security, or governance workflows.

Administrative access and changes should be auditable. The Administrator Media area is not a general shortcut for silently editing Workspace content.

## Storage principles

- Database records and storage objects must have stable identifiers.
- Public URLs should not be used as the primary database identity.
- Originals and derivatives must be distinguishable.
- Storage paths must prevent cross-Workspace collisions.
- Private originals require protected access.
- Deletion of records and storage objects may require asynchronous cleanup.
- Backup, retention, and disaster-recovery policy must be documented before production release.

## API boundaries

The final API contract is not yet approved, but the Media domain will require operations for:

- Initiating upload
- Completing or confirming upload
- Listing Workspace Media
- Reading asset details
- Updating metadata
- Reading processing status
- Selecting compatible assets
- Reading usage
- Archiving
- Deleting when safe
- Retrying failed processing where supported

Large-file transfer should not be assumed to pass through the same application request path as ordinary JSON API calls. The upload architecture requires a separate technical decision.

## Database boundaries

The final schema is not yet approved, but the model must distinguish:

- Media Asset ownership
- Original file identity
- Generated derivatives
- Processing records or jobs
- Content attachments or usages
- Asset lifecycle state

A direct `experience_id` field on the Media Asset is insufficient because assets may be reused.

## Required screen states

Media screens must intentionally design:

- First-use empty library
- Upload in progress
- Processing
- Ready
- Partial batch success
- Validation failure
- Processing failure
- Duplicate detected
- Search with no results
- Permission denied
- Storage limit reached when quotas exist
- Asset in use
- Safe deletion blocked
- Offline or network interruption

## Notifications

The system may provide in-app notification or status feedback for:

- Upload completed
- Processing completed
- Processing failed
- Batch partially failed
- Asset cannot be deleted because it is in use
- Storage limit approached or reached when quotas exist

Email notification is not required for ordinary Media processing unless separately approved.

## Analytics and audit events

Potential product analytics events include:

- Media upload started
- Media upload completed
- Media upload failed
- Existing Media selected
- Asset attached
- Asset detached
- Duplicate detected

Audit-relevant events may include:

- Original globally replaced
- Published asset deleted or deletion attempted
- Administrator accessed or changed Workspace Media

Analytics and audit logging are separate concerns and must not be conflated.

## Out of scope until separately approved

- Cross-Workspace asset sharing
- Public stock Media marketplace
- External cloud-drive synchronization
- AI-generated Media
- AI editing
- Real-time collaborative editing
- Advanced video transcoding
- Digital asset licensing
- Automated copyright verification
- Public upload by visitors

## Open decisions before implementation

The following require dedicated documentation and approval:

1. Supported Version 1 file types and limits
2. Storage provider and upload transport
3. Original and derivative retention policy
4. Panorama projection and dimension requirements
5. Image derivative sizes and formats
6. Video support in Version 1
7. Document support in Version 1
8. Storage quotas
9. Soft-delete and recovery duration
10. Virus and malware scanning
11. Metadata privacy and EXIF handling
12. Batch operation limits
13. Public delivery and caching strategy
14. Database schema
15. API contract
16. Processing worker architecture

## Definition of architecture approval

This document approves the central Workspace Media concept, ownership boundary, reuse model, and high-level workflow.

It does not approve implementation. Development may begin only after the relevant screen, database, API, storage, processing, security, and testing specifications are documented and reviewed.
